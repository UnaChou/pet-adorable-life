## P1 — High Priority

### [shared-pets] Content sharing: co-owners see all diary/product entries for a shared pet
**What:** `get_all_products` and `get_all_diaries` filter by `user_id`. A co-owner only sees their own records, not the pet owner's. The sharing feature is nearly useless for family sharing without this.
**Why:** The stated use case is "family members sharing care responsibility." Without seeing each other's diary entries, the feature delivers an invite flow but not the actual value.
**Pros:** Completes the core value of the shared pets feature.
**Cons:** Requires changing query logic — when `pet_id` is provided and the viewer is a co-owner, drop the `user_id` filter (or UNION both users' content).
**Effort:** S (human: ~2h / CC: ~15min)
**Depends on:** Nothing — can be done independently.

## P2 — Medium Priority

### [shared-pets] Add `viewer` role for vet/caretaker access
**What:** A third role — `viewer` — that can see the pet profile and content but cannot create diary entries, add products, or delete anything. Currently only `read_only` and `editor` exist.
**Why:** The vet/caretaker use case needs tighter permissions than `read_only` (which currently allows pet profile edits). User confirmed this during CEO review.
**Pros:** Enables real-world vet sharing without risk of data modification.
**Cons:** Requires ALTER TABLE pet_shares ADD ... to ENUM, new role checks in product/diary routes.
**Effort:** S (human: ~2h / CC: ~15min)
**Depends on:** Content sharing must be implemented first (otherwise role distinctions on content are moot).

### [shared-pets] Notifications: email co-owners when diary/product entry is added
**What:** When a pet owner or co-owner adds a diary entry or product record, send an email to all other co-owners for that pet.
**Why:** User identified this as the missing "delight" — makes the app feel like a shared family journal rather than a solo database.
**Pros:** High delight-to-effort ratio. Flask-Mail already configured. Pattern mirrors existing invite email.
**Cons:** Adds an async email call to every diary/product creation. Could slow down the save flow if SMTP is slow (consider fire-and-forget or background task).
**Effort:** M (human: ~1 day / CC: ~20min)
**Depends on:** Content sharing should be done first.

### [shared-pets] fix accept_pet_share_invitation rowcount check
**What:** `accept_pet_share_invitation` uses INSERT IGNORE and returns `True` unconditionally. If the INSERT is a no-op (row already exists), it returns `True` and the caller flashes "已加入" even though nothing was inserted.
**Why:** Misleading flash message on double-accept edge case. Low frequency but incorrect behavior.
**Fix:** Check `cur.rowcount > 0` after INSERT IGNORE; return `False` if the share was not actually inserted.
**Effort:** S (human: ~30min / CC: ~5min)
**Depends on:** Nothing.

### [shared-pets] Alias ORDER BY in get_all_pets UNION query
**What:** `ORDER BY created_at ASC` at the end of the UNION ALL in `get_all_pets` has no table alias. MySQL resolves by column name in the result, which works now but is fragile if column ordering ever changes.
**Why:** Silent correctness risk. Also just bad SQL hygiene.
**Fix:** Ensure both SELECT clauses name the column consistently (already true) and add a comment noting the dependency.
**Effort:** S (CC: ~2min)
**Depends on:** Nothing.

## P3 — Low Priority / Future

### [shared-pets] Invitation token enumeration via error message distinction
**What:** `pet_join_page` returns different error messages for "token invalid" vs "invitation not for you." An authenticated user could enumerate valid invitation tokens.
**Why:** Low real-world risk on a personal app, but it's a minor information leak.
**Fix:** Return the same generic error for both cases.
**Effort:** S
**Depends on:** Nothing.

### [shared-pets] owner_user_id in pet_shares is redundant
**What:** `pet_shares.owner_user_id` duplicates `pets.user_id` with no DB constraint enforcing they match. Creates a second source of truth.
**Why:** If a future route sets `owner_user_id` incorrectly, the owner loses the ability to manage their own shares.
**Fix:** Remove `owner_user_id` from `pet_shares`; derive ownership from `pets.user_id` via JOIN.
**Effort:** M (requires migration + all callers updated)
**Depends on:** Nothing, but wait until the content sharing work is done to batch the migration.
